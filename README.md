# BOT-NASEB

بوت Telegram واحد لصفحة **لقاء ونصيب**، بواجهة أدمن وواجهة عميل مع فصل صارم بين البيانات العامة وبيانات التواصل الخاصة.

## الحالة الحالية

المشروع جاهز وظيفياً للتشغيل الأساسي:

- إضافة عرض زواج بلصق النص الخام كما وصل، مع دعم النص العامي والأرقام العربية.
- استخراج وتنظيم البيانات عبر Google Gemini عند ضبط `AI_API_KEY`، مع fallback محلي محافظ لا يخترع معلومات غير موجودة.
- معاينة قبل الحفظ واكتشاف الحقول الأساسية الناقصة.
- PostgreSQL عبر SQLAlchemy، مع جدول مستقل لبيانات التواصل الخاصة.
- تعديل وتعطيل الإعلانات (تعطيل ناعم).
- بحث مباشر من قاعدة البيانات بفلاتر متعددة: الجنس، المحافظة، المدينة، العمر من/إلى، الحالة الاجتماعية، والمهنة.
- فهم طلبات البحث العربية الطبيعية؛ الذكاء الاصطناعي ينظم الفلاتر فقط ثم يتم تنفيذ البحث فعلياً داخل PostgreSQL.
- واجهة عميل لتصفح العروض وإظهار البيانات العامة فقط.
- خدمة «دورولي على شريك مناسب» بنفس محرك البحث المباشر.
- طلب تواصل مدفوع يدوياً بقيمة **5 دولار** عبر شام كاش، مع تسجيل رقم العملية ومراجعة الأدمن.
- لوحة أدمن للطلبات والمدفوعات والإحصائيات ونسخة JSON احتياطية.
- Webhook لـRender و`/health`، مع polling محلي عندما لا يوجد عنوان Webhook عام.

## الخصوصية

رقم الهاتف وTelegram وWhatsApp بيانات خاصة. يتم تخزينها في جدول `profile_contacts` منفصل عن البيانات العامة، ولا يدخل أي منها في serializer العام للعميل.

العميل يستطيع رؤية العرض العام فقط، بينما الأدمن يرى بيانات التواصل. التطبيق لا يضع نصوص الإعلانات أو أرقام التواصل في الـlogs.

## الصلاحيات

التعرف على الأدمن يعتمد حصراً على Telegram User ID الموجود في `ADMIN_USER_IDS`. كل عملية إدارية تعيد فحص الصلاحية داخل الـhandler نفسه، وليس فقط عبر إخفاء الأزرار.

## الذكاء الاصطناعي

طبقة AI موجودة بشكل مستقل داخل `app/services/ai.py`.

- عند إضافة إعلان: يحوّل النص الخام إلى Schema منظمة ثم يتم التحقق منها محلياً.
- بيانات التواصل الخاصة لا تُقبل من AI وحده؛ تتم مطابقتها مع استخراج حتمي من النص الخام قبل الحفظ.
- في البحث: AI يمكنه تنظيم الفلاتر، لكن لا يختار النتائج ولا ينفذ SQL.
- إذا تعذر AI، يستمر parser المحلي المحافظ حيث يكون ذلك آمناً.

## قاعدة البيانات

PostgreSQL هو مخزن التشغيل الأساسي.

الجداول الحالية:

- `profiles` — البيانات العامة للإعلانات.
- `profile_contacts` — الهاتف وTelegram وWhatsApp.
- `orders` — طلبات التواصل والمدفوعات اليدوية.

الصور لا تُخزّن كـBinary داخل PostgreSQL؛ يتم الاحتفاظ بـTelegram `file_id` فقط عند توفر صورة.

أرقام الطلبات وأرقام طلبات الدفع تُولّد بعد إنشاء السجل، بدون placeholder مشترك قابل للتصادم.

## الدفع

قيمة خدمة طلب التواصل الحالية: **5 USD** عبر **شام كاش**.

الدفع ليس آلياً. المستخدم يرسل رقم العملية، ثم يراجع الأدمن الطلب يدوياً ويؤكد أو يرفض العملية.

## المتغيرات

راجع `.env.example`. لا تضع أي Secret في GitHub.

المتغيرات الأساسية:

- `TELEGRAM_BOT_TOKEN` — Token البوت من BotFather.
- `ADMIN_USER_IDS` — Telegram User IDs للأدمن، مفصولة بفواصل.
- `AI_API_KEY` — مفتاح Google Gemini.
- `AI_MODEL` — النموذج، والافتراضي `gemini-2.5-flash-lite`.
- `DATABASE_URL` — رابط PostgreSQL.
- `WEBHOOK_SECRET` — سر Webhook، ويمكن لـRender توليده تلقائياً.
- `WEBHOOK_PATH` — الافتراضي `/telegram`.
- `PORT` — افتراضي 10000.
- `CHAM_CASH_ACCOUNT` — رقم/حساب شام كاش الظاهر للعميل.

## Render

`render.yaml` يجهز Web Service واحداً وقاعدة PostgreSQL، ويربط `DATABASE_URL` تلقائياً.

المشروع لا يستخدم Worker إضافي أو Redis أو تخزين ملفات كبير.

لأجل التشغيل الفعلي على Render، يجب إدخال القيم السرية من لوحة Render أو أثناء إنشاء Blueprint، خصوصاً `TELEGRAM_BOT_TOKEN` و`ADMIN_USER_IDS` و`AI_API_KEY` و`CHAM_CASH_ACCOUNT` عند الحاجة.

## التشغيل المحلي

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
pytest -q
python -m app.main
```

إذا لم يوجد `PUBLIC_BASE_URL` أو `RENDER_EXTERNAL_URL` يعمل البوت محلياً عبر polling.
