# BOT-NASEB UX + AI Hardening Design

## Goal
تحويل BOT-NASEB من بوت وظيفي أساسي إلى تجربة احترافية ومريحة للأدمن والعميل، مع تقليل الاعتماد على الواجهات الجامدة وجعل Gemini يفهم النص السوري الطبيعي ثم يحوله إلى بيانات قابلة للتحقق والبحث.

## UX principles
- كل شاشة مهمة تملك رجوعاً واضحاً إلى الشاشة السابقة أو الرئيسية.
- `/start` يعيد الجلسة إلى نقطة الصفر.
- العميل المبتدئ يستطيع استخدام البوت بدون حفظ أوامر خاصة.
- الأدمن يرى أدوات الإدارة مجمعة وواضحة، مع تأكيد قبل العمليات الخطرة.
- رسائل الخطأ تشرح ماذا يفعل المستخدم بعد الخطأ.
- أزرار callback لا تكون موجودة بصرياً إلا إذا كان مسارها مسجلاً ويعمل فعلياً.

## Client flow
الواجهة الرئيسية تعرض: البحث عن عرض، دورولي على عريس مناسب، دورولي على عروس مناسبة، تصفح العروض، طلبات التواصل، وطريقة العمل.

البحث الحر يقبل أي صياغة طبيعية سورية. عند غموض مؤثر، يعرض البوت فهمه كملخص قابل للتعديل قبل تنفيذ البحث. عند وجود نتائج، تعرض كبطاقات مختصرة مع أزرار للتفاصيل والتنقل. العروض المحجوزة تظهر بوضوح ولا تسمح بإنشاء طلب تواصل جديد.

## Admin flow
لوحة الأدمن تجمع: إضافة إعلان، البحث، الإعلانات، التعديل، التعطيل، الحجز، الحذف، الطلبات والمدفوعات، الإحصائيات، والنسخة الاحتياطية.

إضافة الإعلان: النص الخام -> Gemini structured extraction -> validation -> preview publishable -> edit/cancel/save. لا يتم حفظ البيانات قبل موافقة الأدمن.

## AI contract
### Profile extraction
Gemini يعيد فقط Schema الحالية: gender, name, age, residence, marital_status, children_count, occupation, education, height, weight, appearance, partner_requirements, وبيانات التواصل التي يثبتها النظام من النص الخام. لا توجد حقول مستقلة للجنسية أو الديانة أو المواصفات الشخصية.

### Search extraction
Gemini يحول طلب البحث الطبيعي إلى ProfileFilters فقط. لا يختار النتائج ولا ينفذ SQL.

### Validation
كل قيمة AI يجب أن تُقارن بالنص الخام عند الحقول الحساسة، وأي قيمة غير مثبتة تُرفض. الطبقة المحلية مساعدة للتحقق وليست بديلاً صامتاً عند فشل Gemini عندما يكون AI مطلوباً.

## Data presentation
الموديل العام يستخدم `residence` كحقل سكن موحد. بطاقة/منشور الزواج للأدمن يكون قابلاً للنسخ والنشر، مع رقم الطلب كاملاً. العميل يرى البيانات العامة فقط، ورقم الهاتف لا يظهر مكشوفاً؛ يظل الاتصال الخاص في طبقة منفصلة.

## Booking
الـProfile status: active / reserved / inactive. الأدمن يستطيع الحجز وفك الحجز. العميل يرى حالة محجوزة بوضوح ولا يستطيع فتح طلب تواصل لعرض محجوز.

## Payments
طلب التواصل ينشئ Order بقيمة 5 USD، ويُرسل للأدمن فوراً مع Telegram User ID واسم الحساب وUsername إن وجد ورقم الإعلان ورقم طلب الدفع. الدفع اليدوي يبقى خارج نطاق الأتمتة البنكية، والأدمن يراجع الطلب ويؤكد أو يرفض.

## Reliability
- لا callback بدون handler.
- لا handler بدون مسار conversation مناسب.
- callbacks التي تحتاج رقم طلب تتحقق من الرقم والحالة.
- عمليات الحذف النهائية تتطلب تأكيداً منفصلاً.
- لا تستخدم أزراراً توحي بوظيفة غير مفعلة.
- جميع المزايا الحالية المهمة تبقى موجودة ما لم تتعارض مع هذا التصميم.

## Testing
اختبارات وحدات لمسارات التنقل، callbacks، parsing/normalization، AI schema validation، privacy، booking state transitions، payment notifications، وrepository operations. GitHub Actions يجب أن يشغل الاختبارات على كل push إلى `main` وعلى فرع العمل أثناء التطوير.
